SOC Phish Triage Playbook

Step-by-step guidance aligned with this simulator: intake → investigate → justify → act → resolve.

1 Intake

  1. Open Inbox; filter by Category or Priority.
  2. Note reporter context (hover name for risk profile).
  3. Select a row — details load in the right pane.

2 Investigate

  1. Preview — urgency, impersonation, odd tone.
  2. Headers — From vs Reply-To mismatch?
  3. Auth — SPF/DKIM/DMARC (see next tab).
  4. Links — visible text vs real URL (masked links).
  5. Attachments — risky types; detonate in sandbox if unsure.

3 Decide & document

  1. Choose Threat, Spam, or Clean (or shortcuts T S C).
  2. Pick a reason code that matches evidence.
  3. Write analyst notes (min 20 chars required before Resolve).
  4. Add OSINT/sandbox clips via URLScan or Detonate — they append to notes.

4 Act & close

  1. In Review while analyzing; Resolve when disposition + notes are complete.
  2. For confirmed malicious mail: PhishRIP (same message) or ZAP (sender domain).
  3. Export Shift Report from Dashboard when the exercise ends.
Why this order?

Fast triage balances speed and accuracy: prioritize dangerous mail, verify with headers and links before clicking anything real-world, then record decisions so another analyst could continue the case.

Email authentication tells you whether the sending infrastructure is allowed to send as that domain — not whether the content is safe.

SPF

Sender Policy Framework. Lists which servers may send mail for a domain (DNS TXT).

fail — sending IP is not authorized → spoofing risk.

pass — sending host is allowed → attacker may own a lookalike domain; still analyze body/links.

DKIM

DomainKeys Identified Mail. Cryptographic signature proves the message was not altered in transit.

fail — signature mismatch → tampering or wrong key.

pass — signed consistently → still verify it is your trusted domain, not a typosquat.

DMARC

Domain-based Message Authentication. Tells receivers what to do when SPF/DKIM do not align (policy).

fail — policy violation / alignment failure → strong spoofing signal.

pass — aligned with policy → combine with content review.

Quick mental model
  • SPF = "Is this mail server allowed to send as this domain?"
  • DKIM = "Does this message cryptographically match the sender domain?"
  • DMARC = "What should we do when SPF/DKIM do not align?"

Threat

Malicious intent: credential theft, malware, fraud, or confirmed phishing infrastructure.

  • Use reason codes: Malicious Link, Malicious Attachment, Domain Spoofing, Social Engineering, etc.
  • Run PhishRIP / ZAP when policy allows; document in notes.
  • Consider PhishFlip for training campaigns after containment.

Spam

Unwanted or bulk mail — not necessarily malware, but abusive or misleading.

  • Often graymail, excessive marketing, or low-confidence phishing.
  • Reason codes may still apply (Social Engineering, Authentication Failure).
  • Escalate to Threat if indicators worsen.

Clean

Legitimate internal or expected external mail after verification.

  • Known Safe Sender / Internal Communication reason codes.
  • Resolve with clear rationale so reporters trust the process.

Use these like recipes: ingredients = evidence you collect; steps = order of operations. Names match buttons in the simulator.

Recipe: PhishRIP vs ZAP (Zero-hour Auto-Purge)

ZAP here means proactive purge by sender domain — same idea as "zero-hour" response.

  • PhishRIP — Remove matching instances of this email (same campaign fingerprint) across mailboxes.
  • ZAP — Purge or block mail from the same malicious sender domain more broadly.
  • Rule of thumb: same template everywhere → PhishRIP first; poisoned domain still pumping mail → ZAP.

Recipe: Likely malware / credential phishing (Threat)

  1. Confirm classification: Threat + reason (e.g. Malicious Link, Domain Spoofing).
  2. Evidence: paste OSINT / detonation lines into notes.
  3. Contain: Run PhishRIP if policy matches; add ZAP if the domain is the root problem.
  4. Resolve with ≥20 chars explaining why.

Recipe: Probably unwanted but not malware (Spam)

  1. Spam + reason (Social Engineering, Authentication Failure, etc.).
  2. Block or tag per playbook; escalate to Threat if indicators worsen.
  3. Resolve with coaching notes for the reporter if useful.

Recipe: Verified legitimate (Clean)

  1. Clean + Known Safe Sender / Internal Communication.
  2. Headers + links align; no credential asks.
  3. Resolve so the reporter gets closure.
Assign / In Review / Resolve
Lifecycle: received → in review → resolved. Resolve requires reason + sufficient notes.
PhishRIP
Simulates removing matching message instances across the tenant.
ZAP (Zero-hour Auto-Purge style)
Why it exists: Some campaigns rotate subjects but reuse a bad domain. ZAP simulates org-wide action against that sender domain — faster than remediating one message at a time.
PhishFlip
Turns a contained threat into a training simulation narrative.
URLScan
Pivots to domain search — never substitute for clicking unknown links in production.
Detonate
Sandbox behavior check for attachments; evidence clips notes automatically.
  • Category badges — start as Unknown until PhishML confidence ≥ threshold or you manually classify.
  • Instructor Key — reveals debrief hints in Headers/Auth for class review.
  • Settings → PhishML — adjust confidence thresholds; watch how auto-classification changes.
  • Dashboard — accuracy and disposition mix; download Shift Report for submissions.
  • Final 5 — timer under 5 minutes injects surge traffic; stay calm and prioritize.
  • High Contrast / Mute — accessibility; audio cues fire on resolve, detonation, surge.
  • Reset Lab — clears saved state for the next cohort.

Tip: Treat every incident like production — no clicking dangerous URLs outside controlled tooling.
